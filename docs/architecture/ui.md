# User Interface

The Leptos interface compiled to WebAssembly: views, navigation, the backends and the Aurora Borealis theme.

## Responsibilities

- Render the views and send the user's actions to a backend.
- The theme: Aurora Borealis tokens as CSS custom properties, light and dark.
- It holds no rules: availability, statuses and validation come from the core.

## Structure

| Path | Holds |
|---|---|
| `src/app.rs` | the shell: `View` signal, navigation, Alt shortcuts, theme, shared `AppContext`, preview banner |
| `src/backend/` | `Backend`: `Tauri` (`tauri.rs`) or `Fixture` (`fixture.rs`) |
| `src/views/` | `portfolio`, `project`, `engines`, `inbox`, `messages`, `settings`, `loader` (scheduling of parallel reads), `reads` (row state and reads over the loader, shared by Portfolio and Inbox), and shared helpers |
| `src/theme_contrast.rs` | the contrast test of the tokens |
| `styles/tokens.css`, `styles/app.css` | the theme and the layout |
| `index.html`, `Trunk.toml` | the Trunk build; `trunk serve` listens on port 1420 |

## Behavior

**Backends.** At start-up the interface uses Tauri when `window.__TAURI__` exists, otherwise the fixture backend. The fixture backend answers every command of the desktop from the core's fixtures, and simulates the engine events after a short delay. Each refresh alternates Gedo between ready and degraded, so the preview shows every engine state. A banner says the preview shows sample data. A test checks that the fixture backend answers every command listed in the desktop contracts. For `project_cycle_state` the fixture backend takes `dcp` as ready with the contract, so the views can be built before `dcp` ships it, while the Engines view keeps showing the sample engines; the Portfolio calls it for every project. For the messages commands it takes `dcp-integrations` as ready and answers from `FixtureMessages`, and simulates one background poll a few seconds after start-up.

**Navigation.** One `View` signal: Portfolio, Project, Engines, Inbox, Messages, Settings. The navigation is a list of buttons; the arrow keys move between them, and Alt+1 to Alt+6 open the views. Messages shows "N active" from the snapshot in `AppContext.messages`, with an amber dot when a conversation waits for the user; the snapshot is read at start-up and again after each `messages-snapshot` event with a newer version, on every view. Every focused element has a visible outline. There is no skip link: the sidebar and the content are `<aside>` and `<main>` landmarks, which screen readers jump between, and Alt+1 to Alt+6 also move the focus to the content.

**Views.** Portfolio lists the projects with add (folder dialog or typed path), rename, remove with confirmation, and locate for missing ones, plus the registry notices. Each row shows its project's cycle summary from the core (phase, current release, what waits for the user by kind), or reading, or the failure reason with the engine's error output; the header totals what waits, and Refresh reads every project again keeping the last state until the new one arrives. The reads go through `views::reads` over `views::loader::Loader`: at most four at once, never two for the same project, each answer applied as it arrives, and answers older than the latest request or for a project no longer listed dropped. The unavailable hint is shown once, by the Portfolio's availability line. Engines shows each engine's status, version, location, capabilities, the features it enables, and its last error output, with a Refresh button. Settings holds the theme and each engine's location and time limit. Each Portfolio row has **Open**, which sets the chosen project in the shared `AppContext` and shows the Project view; the choice lasts while Aurora runs and is not saved. The Project view reads the chosen project (the first registered one when none is chosen) through `project_cycle_state`, keeps only the answer of the latest request, and shows one card per section: overview, gates, next step, what waits, plans and milestones, roadmap, release candidate, pull requests, blocking and untriaged bugs; a section with nothing says so. It offers a project choice and Refresh, which keeps the last state until the new one arrives. Failures use `views::CycleFailure`, the same text and engine output disclosure as the Portfolio rows. The Inbox reads every registered project the same way as the Portfolio (its own reads, when it opens) and shows the core's `Inbox`: a header with the items, the projects they belong to, the projects still being read and a note when a project has findings, then one card per urgency with each item's project, kind, title, detail and **Open**, which opens the Project view on its project. Projects that failed are listed under "Not read" through `views::CycleFailure`, or in one line when every failure is the unavailable `dcp`. The Project view has two tabs kept in `AppContext`, **Cycle** (the sections above) and **Settings** (`views::project_settings`): the settings of the chosen project through `project_config`, grouped as the reply groups them, each with a control for its type (choice, check box, text, number as text, check boxes for a list with allowed values, one value per line for a free list), its default when it differs, read-only settings disabled with their reason, and the edits marked. A toolbar counts the edits; **Preview changes** sends the core's `ConfigDraft::change` through `preview_project_config` and shows each key's before and after with the diff; **Apply** sends exactly that change through `apply_project_config`, then reads the settings again and reminds the user to commit `.dev-cycle.json`. Refusals are shown under their field with the accepted values; a stale revision offers to read again, keeping the edits (`ConfigDraft::rebase`). Leaving the tab or choosing another project with edits not applied asks first. In the preview, the fixture backend keeps the sample settings in memory. Every section shows ready, degraded, unavailable with what is needed, or the release that brings it. Messages (`views::messages`) is a chat between projects (ADR-0013) and reads only the snapshot (ADR-0012): `Mailbox` holds it with what the user just did and the next snapshot has not caught up with yet (messages read, decisions sent), applied over the inboxes. The main element drops its padding (`main.flush`) and the view is a grid of three columns: **contacts** (300 px, fixed), **chat** (flexible) and **detail** (closed; `min(440px, 40%)` when a message is open), with the column width animated over 220 ms unless the user prefers reduced motion. Contacts come from `chat_contacts`: picture (the logo from Aurora's project list, else initials on one of six palette colors chosen from the name), name, last summary (`You:` when sent), time (`row_time`), unread badge and an amber dot when a decision waits; a search box filters by name, subjects and summaries. The chat of the selected project comes from `chat_stream` with the browser's time zone: day separators (`day_label`), received bubbles on the left with the sender's picture and name, sent bubbles on the right (`--bubble-out`), each with the summary or the subject, the subject, kind and round on the first bubble of a conversation, a quote of the message answered (a click scrolls to it), the kind, time and the delivery mark (✓, ✓✓, ✓✓ in the accent color when handled, a clock when set aside) or "● new". A header shows the counts and a `With:` filter by counterpart; it opens scrolled to the newest message and offers "Newest ↓" when the user scrolled up. Closing records are cards in the stream: the decision card while it waits (a click sends `decide` after a 5 s Undo window; "Something else…" sends the user's words or `revise`), a green closed card with the choice, or, in the other project's chat, a card that links to the project that decides. A click on a bubble outlines it and opens the detail panel: from → to, subject, kind, date and round, "Summary by the sender", the message body (lead sentence, sections, Next step callout, Authority and Open points folded, "✓ Handled by …"), **Reply** (to that message, when received) and **Step in**; a received unread message is marked seen through `messages_act` at once. Escape or ✕ closes the panel; Up and Down move between bubbles. **New conversation** opens under the chat from the selected project. Reply and New conversation have a Summary field with a counter (at most 280 characters, checked by the core before the provider). Forms come from `messages_template`, required sections marked; a refusal is shown next to the form with the missing sections, and a Git failure with its output. Results and errors go to a polite live region. Portfolio rows show the project's picture and offer **Logo…** and **Remove logo**.

**Theme.** `<html data-theme>` is `light` or `dark`, resolved from the setting and from `prefers-color-scheme` while the setting is "system". The dark tokens come from AnyContext's `AuroraTheme`, with muted text lightened to `#94A3B8` and errors to `#F87171` for contrast; the light tokens are derived. The test checks every text and background pair at 4.5:1 and focus indicators at 3:1, in both themes. Views use classes only, no inline styles, to fit the content security policy.

## Interfaces

Calls `aurora-desktop` commands and listens to its events; uses the types of `aurora-core`.

## Decisions

- [ADR-0002](../adr/0002-desktop-application-with-tauri-2-and-a-leptos-interface.md): Leptos interface, all Rust.
- [ADR-0012](../adr/0012-a-messages-worker-in-aurora-owns-every-provider-call-and-ser.md): the Messages view reads only the snapshot; writes go through the worker queue.
- [ADR-0013](../adr/0013-messages-read-as-a-chat-between-projects-with-a-summary-writte.md): Messages as a chat between projects in three columns; project logos.
- [ADR-0014](../adr/0014-aurora-is-a-self-hosted-web-application-governed-by-the-levi.md): the interface gets an HTTP backend for the Aurora web server.
- [ADR-0015](../adr/0015-integrations-coordinator-round-tables-approvals-by-every-inv.md): Messages as a list of round tables, a group chat per table and an approval strip per involved project.
