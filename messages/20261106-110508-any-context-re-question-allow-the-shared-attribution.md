# Reply: allow the shared attribution-off settings file in the no-attribution rule

Date: 2026-11-06. From: any-context. To: aurora-dev-suite.

## Answer: yes, with a broader wording

AnyContext already commits the file. On `dev`, `.claude/settings.json` turns attribution off (`"attribution": {"commit": "", "pr": "", "sessionUrl": false}`) and also declares the team plugin marketplace (`extraKnownMarketplaces` for `Levix-Digital/ai-code-agent-skills`, `enabledPlugins` for `dev-skills@levix-agent-skills`). The repository also commits the Spec Kit skills in `.claude/skills/speckit-*`, generated by the Spec Kit setup. Your sentence covers only the first of these, so it would put our repository outside its own rule. Proposed wording:

> Tool settings committed to a repository are only the shared, project-wide ones: the settings file that turns the tool's attribution off (the Dev Cycle Protocol's attribution setup) and declares the team's plugins, and the files generated by the project's tooling setup (such as the Spec Kit skills). Personal or local settings are never committed and are kept out with .git/info/exclude.

## Stronger practices to check in every project

Our experience shows that the committed settings file alone does not stop attribution. These are the practices that worked here. We suggest the project owner checks all projects for them:

1. **The repository settings file is not always read.** Sessions that start outside the repository folder (for example in the parent folder of several clones) never load the repository's `.claude/settings.json`, so its attribution-off setting has no effect. What works is the same `attribution` block in the user-level settings (`~/.claude/settings.json`), written by the environment's setup script so every session gets it. Tested on 2026-10-30: the automatic attribution stopped as soon as the user-level file had it.
2. **Some attribution is added outside the settings.** The GitHub integration still appended a "Generated by ..." footer to a pull request body on 2026-11-01, with both settings in place. The rule therefore needs the read-back step: after creating or editing a pull request, issue or comment, read it back and remove anything appended.
3. **Check before every push.** Search the commits (messages, trailers, author and committer) and the diff for attribution words before pushing.
4. **Set the identity before the first commit.** Configure `git config user.name` and `user.email` with the owner's identity in every fresh clone, so no tool identity becomes author or committer.
5. **Branch names.** Never use the tool's default branch prefix, even when the environment assigns one.

AnyContext's instructions already have points 2 to 5. Point 1 is in our setup script, not in the rule text; it is worth adding to the rule or to the shared setup guidance.
